How it works

Small developer action, large amount of automation

Every arrow below is automated and running today. Git stays the record of what runs where: automation writes commits, never directly to a cluster.

  1. Backstage

    Onboard Service template renders the request and opens the PR as a GitHub App bot.

  2. application-repositories

    The GitOps repo. A reviewed merge is the only manual step.

  3. Argo CD

    ApplicationSets on the management cluster turn files into Applications, push-triggered by webhooks.

  4. component-operator + Crossplane

    Component owns a GitHubRepository; Crossplane creates the repo and its Argo CD webhook.

  5. scaffold-operator

    Renders a versioned platform-scaffolds template into the repo in one commit: Go service, Dockerfile, Helm chart, CI, catalog entry.

  6. GitHub Actions

    Tests, builds and pushes the image; chart and image ship from the same commit.

  7. release-operator

    Sees the green build and commits that exact version for dev: a revertable Git commit, not a cluster write.

  8. Kubernetes (EKS)

    Two replicas behind an ALB with DNS and TLS from external-dns and ACM, a PodDisruptionBudget and a ServiceMonitor.

  9. Observability

    Prometheus remote-writes to central Mimir; Grafana and the portal's Metrics tab read one store for every environment.

Design decisions

The choices behind it

The full reasoning lives in the architecture docs.

A small API, not a mega-CRD

Component is just an identity record. Databases, releases and queues are independent resources that point back to it, so each can evolve on its own instead of turning one CRD into an orchestration engine.

Git is the record of what runs where

Onboarding, deploys and auto-deploys all end as commits in one GitOps repo. Every change is reviewable and revertable, and the cluster can be rebuilt from Git.

Bots, not personal tokens

The portal, the scaffolder and the release automation each commit as their own GitHub App with short-lived, narrowly scoped tokens; CI reaches AWS through OIDC with no stored secrets.

Disposable clusters, durable state

The EKS clusters are created and destroyed daily to keep cost down. DNS, certificates, secrets and Terraform state live outside them, so a fresh cluster converges from Git in minutes.

Safe to show the public

Guests browse the live portal read-only. Metrics come from fixed server-side queries, so a visitor can't send PromQL; logs and templates are owner-only.

Observability by default

Every scaffolded service exposes the same metrics and identity labels, so one dashboard and one portal tab cover every service and environment with no per-service setup.
